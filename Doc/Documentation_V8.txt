📌 مقدمه و هدف
================================================================================

این سند به عنوان مرجع اصلی برای پیاده‌سازی بخش Backend پروژه CRM با استفاده از
.NET 10 و معماری Clean Architecture (با رویکرد ساده و قابل فهم) تهیه شده است.

⚠️ **نکته مهم**: مرجع اصلی و مبنای تمام پیاده‌سازی‌ها، **.NET 10** است. تمام کدها،
کتابخانه‌ها، تنظیمات و بهترین شیوه‌ها باید بر اساس این نسخه از دات‌نت باشد.
هر گونه تغییر در معماری، کتابخانه‌ها یا روش‌های پیاده‌سازی باید با این نسخه
سازگار باشد.

اهداف اصلی:
1. سادگی: از پیچیدگی‌های غیرضروری پرهیز شود
2. قابلیت توسعه: معماری به گونه‌ای باشد که افزودن ماژول‌های جدید در آینده آسان باشد
3. شفافیت: جریان داده و کد باید به راحتی قابل درک باشد
4. آموزشی: هر مرحله توضیح داده شود تا اگر مطلب جدیدی بود، قابل یادگیری باشد
5. **هماهنگی با .NET 10**: استفاده از جدیدترین امکانات و بهبودهای این نسخه

اطلاعات فعلی پروژه:
- یک وب اپلیکیشن CRM با Backend دات‌نت 10
- دو نقش: کاربر عادی و اپراتور
- ماژول تأییدشده: اطلاعات مشتری (برای اپراتور)
- ویژگی خاص: سیستم نمایندگی با ساختار والد-فرزندی برای کاربران
- سیستم امتیازدهی: زیرمجموعه‌ها با تماشای فیلم برای نماینده اصلی امتیاز کسب می‌کنند

🏗️ معماری انتخاب شده
================================================================================

معماری کلی: Clean Architecture (ساده‌شده) مبتنی بر .NET 10

┌─────────────────────────────────────────────────────────────┐
│                    API Layer (Crm.Api)                      │
│  Controllers, Middleware, Program.cs, appsettings.json      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                Application Layer (Crm.Application)          │
│  Use-Cases (Commands/Queries), DTOs, Validation, Interfaces │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   Domain Layer (Crm.Domain)                 │
│  Entities, Value Objects, Repository Interfaces             │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│              Infrastructure Layer (Crm.Infrastructure)      │
│  EF Core, Repository Implementation, External Services      │
└─────────────────────────────────────────────────────────────┘

اصول کلیدی معماری:
1. Dependency Rule: وابستگی‌ها فقط از بیرون به داخل است (API ← Application ← Domain)
2. Domain لایه: هیچ وابستگی به لایه‌های دیگر ندارد
3. Application لایه: فقط به Domain وابسته است
4. Infrastructure: پیاده‌سازی جزئیات فنی (دیتابیس، Redis، ...)
5. API: فقط لایه HTTP و ورودی/خروجی

📄 GetUsers
--------------------------------------------------------------------------------

GetUsers به صورت Paginated پیاده‌سازی شده است.

مدل عمومی Pagination:

namespace Crm.Application.Common.Models;

public sealed record PaginatedResult<T>(
    IReadOnlyList<T> Items,
    int PageNumber,
    int PageSize,
    int TotalCount)
{
    public int TotalPages =>
        (int)Math.Ceiling(TotalCount / (double)PageSize);
}

مدل درخواست Pagination:

namespace Crm.Application.Common.Models;

public sealed record PaginationRequest(
    int PageNumber = 1,
    int PageSize = 10);

Response مربوط به GetUsers:

public sealed record GetUsersResponse(
    long Id,
    string UserName,
    string Phone,
    string? Name,
    string? LastName,
    long? ParentUserId,
    bool IsActive,
    bool IsSuperAdmin);

Query خروجی زیر را دارد:

PaginatedResult<GetUsersResponse>

قوانین فعلی Pagination:
- PageNumber >= 1
- PageSize بین 1 تا 100

PaginationRequest فعلاً به عنوان مدل عمومی ایجاد شده است.
استفاده عمومی از آن در تمام Queryهای لیستی در مرحله استانداردسازی Pagination بررسی خواهد شد.

--------------------------------------------------------------------------------

AutoMapper در Application فعال شده است.

ثبت فعلی:

services.AddAutoMapper(config =>

AutoMapper برای Mapping بین Entity و Response و همچنین Mapping Command به Entity استفاده می‌شود.

در UpdateUser، فیلدهای حساس و Audit نباید توسط Mapping تغییر کنند.

نمونه Mapping:

CreateMap<UpdateUserCommand, User>()
    .ForMember(x => x.Id, opt => opt.Ignore())
    .ForMember(x => x.PasswordHash, opt => opt.Ignore())
    .ForMember(x => x.IsActive, opt => opt.Ignore())
    .ForMember(x => x.IsSuperAdmin, opt => opt.Ignore())
    .ForMember(x => x.IsDeleted, opt => opt.Ignore())
    .ForMember(x => x.CreatedAt, opt => opt.Ignore())
    .ForMember(x => x.LastUpdate, opt => opt.Ignore());

CreateMap<User, UpdateUserResponse>();

📄 UpdateUser
--------------------------------------------------------------------------------

برای UpdateUser از PATCH استفاده شده است، زیرا این Use-Case یک Partial Update است و
قرار نیست کل Entity کاربر جایگزین شود.

Endpoint:

PATCH /api/v1/users/{id}

Id از Route دریافت می‌شود و داخل Body ارسال نمی‌شود.

نمونه:

PATCH /api/v1/users/10

Body:

{
  "userName": "ali",
  "phone": "09121234567",
  "name": "Ali",
  "lastName": "Ahmadi",
  "parentUserId": 5
}

Command:

public sealed record UpdateUserCommand(
    long Id = 0,
    string UserName = "",
    string Phone = "",
    string? Name = null,
    string? LastName = null,
    long? ParentUserId = null)
    : IRequest<UpdateUserResponse>;

Controller مقدار Id را از Route به Command منتقل می‌کند:

command = command with { Id = id };

در نتیجه Id نیازی به ارسال در Body ندارد.

--------------------------------------------------------------------------------
📄 UpdateUser Business Rules
--------------------------------------------------------------------------------

در Handler موارد زیر بررسی می‌شوند:

1. User موردنظر باید وجود داشته باشد.
2. UserName نباید متعلق به User دیگری باشد.
3. User نمی‌تواند Parent خودش باشد.
4. ParentUser در صورت وجود باید وجود داشته باشد.
5. ParentUser در صورت وجود باید Active باشد.
6. تغییر Entity با AutoMapper انجام می‌شود.
7. LastUpdate توسط سرور تنظیم می‌شود.
8. سپس UnitOfWork.SaveChangesAsync اجرا می‌شود.

فیلدهای زیر توسط UpdateUser عمومی قابل تغییر نیستند:

- PasswordHash
- IsActive
- IsSuperAdmin
- IsDeleted
- CreatedAt
- LastUpdate
- Id

📄 EF Core Tracking و AsNoTracking
--------------------------------------------------------------------------------

برای جلوگیری از Tracking غیرضروری، متدهای Read که فقط برای بررسی وجود داده استفاده می‌شوند
با AsNoTracking اجرا می‌شوند.

GetByUserNameAsync فقط برای بررسی وجود/تکراری بودن UserName استفاده می‌شود و باید
AsNoTracking داشته باشد:

public async Task<User?> GetByUserNameAsync(
    string userName,
    CancellationToken cancellationToken = default)
{
    return await context.Users
        .AsNoTracking()
        .FirstOrDefaultAsync(
            u => u.UserName == userName && !u.IsDeleted,
            cancellationToken);
}

این متد در CreateUser و UpdateUser برای existence check استفاده می‌شود و Entity حاصل
از آن تغییر داده نمی‌شود.

برای User اصلی که قرار است Update شود، Entity باید Tracking شده باشد.
به همین دلیل متد جداگانه زیر استفاده می‌شود:

Task<User?> GetByUserIdForUpdateAsync(
    long userId,
    CancellationToken cancellationToken = default);

پیاده‌سازی:

public async Task<User?> GetByUserIdForUpdateAsync(
    long userId,
    CancellationToken cancellationToken = default)
{
    return await context.Users
        .FirstOrDefaultAsync(
            u => u.Id == userId && !u.IsDeleted,
            cancellationToken);
}

در این متد AsNoTracking استفاده نمی‌شود تا EF Core تغییرات Entity را هنگام
SaveChanges تشخیص دهد.

🔐 تصمیم فنی: Password Hashing
================================================================================

روش انتخاب‌شده برای Password Hashing: Microsoft.AspNetCore.Identity.PasswordHasher<User>

دلیل انتخاب:
- پیاده‌سازی استاندارد Password Hashing در ASP.NET Core Identity است.
- دارای API استاندارد برای HashPassword و VerifyHashedPassword است.
- از نگهداری رمز عبور خام جلوگیری می‌کند.
- منطق Hashing در Infrastructure قرار می‌گیرد و Application فقط به abstraction یعنی IPasswordHasher وابسته است.
- در صورت نیاز به تغییر پیاده‌سازی در آینده، Login Use-Case نیاز به تغییر نخواهد داشت.

ساختار: 
Application/Domain → IPasswordHasher
Infrastructure → PasswordHasher : IPasswordHasher

نکته: PasswordHash فقط در فیلد User.PasswordHash ذخیره می‌شود و Password خام هرگز ذخیره نمی‌شود.

مرجع رسمی: Microsoft Learn - PasswordHasher<TUser> در ASP.NET Core/.NET 10
